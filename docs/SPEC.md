# Unsub — Spec

A desktop music player for people who own their music. Looks and behaves almost exactly like iTunes 10 (2010–2012), with features for a buy-to-own, self-hosted world instead of a store and a streaming service.

## Decisions

| Area | Decision |
|---|---|
| Visual target | iTunes 10 (10.0–10.7), Mac look on both platforms |
| Platforms | macOS + Windows |
| Stack | Tauri 2 shell · Rust core crates · React + TypeScript UI drawn entirely by us |
| License | GPL-3.0-or-later |
| Media kinds | Music, Podcasts, Audiobooks (no video) |
| Brand mark | Vinyl record (replaces the Apple logo in the LCD and the app icon) |
| Distribution | Direct download, Developer ID signed + notarized (owner has an Apple Developer account). Not the Mac App Store: the custom window frame needs `macOSPrivateApi`. |

## Clean-room rules

1. No Apple code, binaries, images, nibs, strings or fonts in this repo. Every visual is redrawn in CSS/SVG.
2. Apple resources may be used only as a **measuring reference** (sizes, positions, colors) from outside the repo.
3. No Apple logo, no "iTunes" name or icon anywhere in the product.
4. Fonts: system Lucida Grande on macOS, Lucida Sans Unicode on Windows. Never bundled.

## Architecture

```
src/                 React UI (the iTunes 10 window, drawn by us)
  theme/tokens.css   every measured size and color, one place
  chrome/            toolbar, LCD, transport, volume, view buttons, search, traffic lights, bottom bar
  sidebar/           source list (Library, Purchases, Devices, Shared, Mixes, Playlists)
  browser/           song list, album list, grid, Album Artwork
  api/               typed wrappers around Tauri commands/events
src-tauri/           Tauri shell: window, commands, events, app state
crates/library/      SQLite library: scan, tags, artwork, queries, smart playlists, import
crates/playback/     decode (symphonia) + output (cpal; bit-perfect backends later)
```

The UI never touches files or audio directly; it calls commands and listens to events. This mirrors iTunes' own split (portable C++ core, thin platform shell, self-drawn toolkit).

## Milestones

Each milestone ends with something you can run.

1. **Shell** — the iTunes 10 window, pixel-matched, with static data. Window chrome works (drag, resize, minimize, zoom, close) on both platforms.
2. **Library** — add folders, read tags, store in SQLite, song list with sort/search, status bar totals. Virtualized for 100k tracks.
3. **Playback** — play/pause/seek/next/previous, volume, LCD progress, play counts. FLAC, ALAC, AAC, MP3, Vorbis, WAV, AIFF.
4. **Playlists** — playlists, folders, drag-and-drop, ratings, smart playlists (iTunes rule editor), Party Shuffle with Up Next.
    - **Right-click in the source list:** the row is outlined while its menu is up and the page being viewed stays. A playlist: Play, Shuffle, Edit Smart Playlist… (smart only), Rename, Duplicate (placed just after it, with the same songs, in order), Export Playlist…, Delete Playlist…. A folder: New Playlist in Folder, New Folder in Folder, Rename, Delete Folder… (which says how many playlists go with it). An iPod: Sync, Copy Music to Library…, Eject; a player: Eject; a CD: Import CD (with the saved import settings) or Stop Importing, Eject Disc; a shared library: Disconnect; Podcasts: Update All Podcasts. Edit › Delete deletes the selected playlist or folder while the source list has focus.
    - **Export Playlist…** writes an M3U8 file: UTF-8, `#EXTM3U`, then for each song `#EXTINF:<seconds>,<artist> - <title>` (`-1` seconds when the length is unknown) and its path, in playlist order. Stations are left out; songs that are cloud placeholders or missing from disk keep their entry.
5. **Import** — Music/iTunes library import (XML and macOS iTunesLibrary.framework): play counts, ratings, playlists, date added.
6. **Album views** — album list, grid, Album Artwork, artwork fetching (MusicBrainz / Cover Art Archive).
7. **Lossless / audiophile** — Opus, WavPack; bit-perfect output (Core Audio hog mode + sample-rate switching; WASAPI exclusive).
8. **Podcasts & Audiobooks** — RSS subscriptions, auto-download, played state, chapters, resume position.
    - **Finding podcasts:** Find Podcasts… in the Podcasts view has Top Shows (by category) and Search tabs, each result with a Subscribe button. Search runs on Return or 400 ms after the last key; charts are cached for the session. All directory requests are made in Rust (the CSP allows no network from the page) behind the `Directory` trait in `crates/podcasts/src/directory.rs`; the source is Podcast Index when the build was given `PODCASTINDEX_API_KEY` and `PODCASTINDEX_API_SECRET` at compile time (release builds are, from repository secrets; the values are never logged), and Apple's public podcast directory (no key) otherwise or for any request Podcast Index fails. Apple's charts and search use the region of the OS locale, `us` if unknown. The directory UI names the directory that answered the latest request, once, in one plain line, and shows no Apple logos or art. Charts are cached for the session, except that a chart the fallback answered is asked of Podcast Index again after 5 minutes. A show counts as followed if its feed, or the address it was subscribed with before a redirect, matches.
    - **Import from Podcasts app (macOS only):** reads the followed shows from the app's library (`MTLibrary.sqlite` in its group container) from a private copy, never the live file, and only after the user clicks the button, since that read is what makes macOS ask for permission. The shows come as a checklist, all ticked, with those already subscribed marked and disabled; the ticked ones go through the normal subscribe, one at a time, and any that fail are listed.
9. **CD ripping** — ALAC/FLAC/AAC, MusicBrainz disc lookup, AccurateRip verification.
9b. **Own your streaming**: compare your Apple Music library against what Unsub holds.
    - Read the library via `iTunesLibrary.framework` on macOS (permission prompt), or from an exported Library XML on Windows or as a fallback.
    - Classify every song: in Unsub / owned file to import / bought but not downloaded / uploaded or matched in iCloud / subscription-only (to buy).
    - Sidebar "To Own" under PURCHASES: a progress count ("412 of 1,203 owned"), one-click import of owned files, and a buy list grouped by album with store links.
    - Re-checks automatically as new purchases arrive.
9c. **iCloud libraries:**
    - **iCloud Drive folders:** add them like any folder. Evicted (cloud-only) files are recognized without forcing a download, then fetched on demand when played, or pinned to stay local. Progress is shown in the LCD.
    - **Song details from iCloud:** Advanced › Get Song Details from iCloud… (macOS and Windows) reads the real tags and cover of the songs that are only in iCloud, which until then are known by their file names alone (no genre, year, length or cover). The sheet says how many songs there are and what downloading them comes to, and Start hands the work to the background: one song at a time, each downloaded, read, its cover kept, and given back to iCloud, never writing to a music file. On a Mac it works only on files in iCloud Drive's own folder (`~/Library/Mobile Documents`), since it can't give back what another provider (Dropbox, Google Drive, OneDrive) put there. Only files the job itself downloaded are given back, and never the song playing or queued next (it is given back once playback has moved on). Each download is first written to the same small list in the app cache that an iPod sync keeps, and struck off once the file is a placeholder again, so a file that lands after the job gave up on it, or was held when the app quit, is given back at the end of the run, at the next launch or at the next sync (unless the song was played meanwhile). That giving back, like the job's own, leaves alone the song playing or queued next, and a sync leaves alone the downloads of a job that is still going. The job waits while a song is being fetched for playing. It pauses itself with a notice, to be resumed from the sheet or the LCD, if the disk has less than 10 GB (or three times the song) free once the songs it gave back have had time to leave, if three downloads in a row bring in nothing, if five songs in a row have no file while their library folder, the first folder below iCloud Drive's (Music, say), is gone too, as when iCloud Drive is off or the folder is renamed (while it is there, a song with no file was deleted and is flagged missing, wherever in it, and nothing pauses), or if the system keeps declining to take files back (each is asked three times). A song that comes down unreadable is remembered by its file's size and date and not downloaded again until the file changes; one that can't be downloaded is tried again next time. Only songs never read are selected, so a newer tag parser doesn't send all of them through it again, and a song that was read stays read when it is edited or its library is imported again while it is in the cloud, as long as its file is unchanged. It carries on where it left off after a quit, if their library folder is there (which songs are read is in the library; a "wanted" setting says whether it was going). The notice at the end counts songs read, skipped and not found. Each cover is kept once per distinct picture (at most 512 pixels) in a `Covers` folder beside the library's database, which the `artwork:` protocol serves while the song is back in iCloud; thumbnails made from it are cached with the rest of the artwork, and covers of songs that have left the library are tidied away at the end of a run.
    - **iCloud Music Library:** To Own's Re-download group gets "Download from iCloud". Unsub asks the Music app to download purchased and uploaded/matched songs (Music's scripting `download` command, one-time Automation permission), then imports the files. Subscription songs can't be downloaded and stay on the buy list.
    - **Later:** read the cloud library directly via the Apple Music API (MusicKit, owner's developer account), without Sync Library. Metadata only.
9d. **Leaving a streaming service:** bring your playlists and listening history from Spotify, YouTube Music or ListenBrainz (and Last.fm, through ListenBrainz).
    - **Where:** File › Import from Spotify, YouTube Music or ListenBrainz…, a sheet with a tab per service, short steps with a link to where that service hands out its export (Spotify's privacy page notes the extended history can take days to arrive), then a file, ZIP or folder to read. Exports are read where they are: nothing is uploaded, and no account or API key is needed. A ZIP is unpacked to a temporary folder, only its JSON and CSV files and only up to a few gigabytes, and the folder is removed afterwards.
    - **What is read:**
      - **Spotify:** "Account data" (`Playlist*.json`, the saved songs in `YourLibrary.json` as "Liked Songs", and the last year of plays in `StreamingHistory_music_*.json`) and "Extended streaming history" (`Streaming_History_Audio_*.json`, or `endsong_*.json` in older exports: every play, with its album). Exportify's playlist CSVs too, whatever language it ran in. Podcasts, audiobooks and videos are skipped, local files in a playlist are read from their `spotify:local:` address, and any play under 30 seconds is skipped, which is Spotify's own threshold for a stream. The IP addresses and devices in the extended history are never read.
      - **YouTube Music, from Google Takeout:** the YouTube Music entries of `watch-history.json` and the playlist and saved-song CSVs. Only songs from an artist's auto-generated "Topic" channel are taken from the history, since a music video or an upload has no song and artist to read out of it. Google's playlist files list only video IDs, so they are named from the history and saved songs that know the same video, and the ones nothing can name are counted and said so. Google writes "Watched" in the account's language; only English is read.
      - **ListenBrainz:** its export ZIP (`listens/<year>/<month>.jsonl`). Last.fm has no file export, so the sheet says to import Last.fm history into ListenBrainz first, which ListenBrainz does itself.
    - **Matching:** each song is matched to the library with the same rules as the Music import: artist and title with release notes and featured artists ignored, length within a few seconds when the export gives one, and the album as the tiebreaker. A song that fits songs on different albums equally well is never chosen for you; it is counted as ambiguous and left out. A very common title ("Intro", "Interlude", "Skit"…) needs the album or the length to agree, and a Spotify play can't be of a track shorter than the song is usually played for. A song whose candidates fail only for want of such evidence is counted as ambiguous, not missing, so it is left out rather than sent to To Own. The sheet shows "12 playlists · 1,204 songs · 82% matched" and "48,210 plays · 76% matched" before anything changes, and Import uses those matches unless a track has since gone.
    - **Playlists:** made in a folder named for the service ("From Spotify"), in the export's order, with only the songs that matched. Importing again replaces the contents of the playlists it made, in place, instead of making copies: each is remembered by service and name (capitals, underscores and punctuation don't matter) in `ImportedPlaylists.json`, as the Music import remembers its own. A playlist id is never given out again (the library keeps the highest it has handed out), so a remembered id still means its playlist for as long as it exists, and the Music import relies on the same: a playlist renamed in Music, or here, is named as Music has it on the next import, while one renamed here from a Spotify or YouTube export keeps its name.
    - **Plays:** added to the play log, tagged with the service, and to each song's play count and last played, unless "Add plays to play counts" is off (it is on by default). A play is one song at one time: the log ignores a play it already has from the same service, even if the song has since matched another copy of itself, and a play that is the same listen as one another service recorded: within the song's length plus two minutes of it, since services stamp a listen at its start or its end. A recorded listen absorbs at most one play, the nearest, so three real plays aren't made one by a single listen elsewhere. So importing again, importing both of Spotify's exports, or Spotify and then ListenBrainz (which often records the same listens) counts each once. Plays the Music app scrobbled can't be told apart from Music's own play counts, and may count twice. A long history goes in 5,000 plays at a time while the LCD follows. The Music import adds the plays logged here (by Unsub or a service) to Music's count, whichever comes first.
    - **To Own:** songs in playlists with no match are listed there beside the Apple Music ones, grouped by album with the same store links, and labelled with where they came from ("Spotify playlist “Road Trip”"; a song several playlists or services found carries each place). History-only songs are listed once they've been played twice: one listen is as likely a shuffle as a song worth owning. A song the Music library also lists is that row, not a second one to buy. They leave the list once the library has them, and a row's × or "Forget <service> Songs" takes them off sooner.
9e. **First run:** a welcome sheet, in the spirit of iTunes' setup assistant, that is only a front door to what the menus already do.
    - **When:** at launch, if the library holds no songs (music, podcasts and audiobooks count; stations and the stock playlists don't) and the `welcomed` setting isn't set. `welcomed` lives in the library database's settings table, not the WebView's storage, which can be reset. Any library that has songs is marked welcomed the first time it is asked, so deleting every song later never brings the welcome back, and nobody upgrading with a library sees it. Help › Welcome to Unsub… opens it again.
    - **Rows:** Import from the Music app (macOS; opens File › Import Music Library, and says plainly that songs only streamed from Apple Music can't play outside Apple's app and go on To Own), Add a music folder (the existing Add to Library with its LCD progress and notices, plus one button each for `~/Music` and the iCloud Drive Music folder when they exist and hold something, and Choose Folder…), Bring your Spotify playlists (opens File › Import from Spotify, YouTube Music or ListenBrainz…), and, only while an iPod is connected, a row that opens its page. Without one, a hint says it will show up under Devices.
    - **Folder detection:** `~/Music` is offered when listing its own names finds one that isn't hidden and isn't Unsub's own media folder; the listing stops at the first, goes no deeper and never opens a file. The iCloud Drive Music folder is offered when it exists and is a folder, from a stat alone: on macOS even listing it can raise the iCloud Drive privacy prompt before the user has chosen anything, so its contents are first read by the import the user starts with it.
    - **Options:** "Keep my media folder organized" (off: only Unsub's own media folder is ever filed, and music added from elsewhere is never moved) and, in builds that can update, "Check for updates automatically" (on). Both are the Preferences settings, applied by Done or by picking a row; Skip applies nothing.
    - **Remembered** when the user picks a row, Done or Skip. After a row that brings in music, the first songs to arrive set off three one-line tips in the LCD, unless a notice about the import is showing.
10. **Purchases** — watch Downloads for Bandcamp/Qobuz/7digital archives, auto-import, "where to buy" links from MusicBrainz.
11. **Mixes** — on-device "more like this" playlists from play history and tags.
12. **Own-your-cloud** — built-in Subsonic-compatible server so phone apps stream your library; client mode for Navidrome.
3b. **iPods, read side** (built alongside milestone 3):
    - Connected iPods appear under DEVICES with an eject button, and their songs and playlists can be browsed and played straight off the device.
    - The Summary page shows the model, the capacity bar and the serial number.
    - Reads `iTunesDB`, or the compressed `iTunesCDB` on nano 6G/7G, merged with the device's `Play Counts` file. No checksum is needed to read.
13. **iPod sync** — classic iPods exactly the way iTunes did it. DEVICES sidebar section with eject, the iPod summary page, the colored capacity bar, and Sync.
    - Write `iTunesDB`, `ArtworkDB` + `.ithmb` thumbnails, and `iTunesSD` for shuffles. The format is reverse-engineered; gtkpod/libgpod are the reference.
    - Checksums: HASH58 for classic 6G/7G and nano 3G/4G (keyed by the FireWire GUID = USB serial number), HASH72 for nano 5G. When the iPod's own files don't give the GUID, macOS reads it from the USB serial number of the iPod behind the volume.
    - An iPod with no database yet (just restored, or never synced) still appears under DEVICES, recognised by its `Device/SysInfo` or `iTunes` folder; its first sync makes the music folders it lacks and writes the database. One that has music but no database is refused, and the preview says so, rather than hiding its songs.
    - A long sync commits what it has copied every 500 songs or 4 GB, and Stop commits what is copied so far, so the iPod keeps those songs and the next sync carries on from there. Songs a sync removes go only in its last commit, so a stop or a failure never takes any away (unless there was no room without). A first sync commits an empty database before copying anything, and a sync that died while copying leaves a list of the files it was copying, which the next sync deletes if the database doesn't use them. A song that won't convert is left out, not a reason to end the sync.
    - **Songs only in iCloud:** a sync downloads them one at a time as it reaches them, shows "Downloading from iCloud" on the LCD, and a song that can't be fetched is left out and counted in the notice at the end (after three downloads in a row time out, the rest are skipped at once). "Remove downloaded songs from this Mac after syncing" (on by default) gives each back to iCloud once it is on the iPod (`brctl evict` on macOS; unpinning on Windows), so the library never has to fit on the Mac. Only songs the sync itself downloaded are ever given back, including ones that finish downloading after it gave up on them (kept for a day in a small list in the app cache, and given back at the next sync or launch if that iPod's setting is still on).
    - Two-way sync of play counts, ratings and on-the-go playlists.
    - Transcode during sync: FLAC/Opus → ALAC or AAC, 24-bit → 16-bit/48 kHz.
    - Supported: iPod classic, video, mini, nano 1G–5G, shuffle 1G–4G. Not supported: nano 6G/7G (HASHAB is uncracked), iPod touch/iPhone/iPad (Apple-private sync protocol).
13b. **Copy to Library** — rescue the music trapped on an old iPod. iTunes never let songs back off one; Senuti and SharePod did. Works on every iPod Unsub can read, including the models it can't sync to.
    - **Where:** the iPod's Summary page has **Copy to Library…**, which opens a sheet: All songs or Selected playlists, "Skip songs already in my library", "Bring play counts and ratings", "Recreate playlists", and a count before anything happens ("5,134 songs · 4,812 new · 41 copy-protected · 18.2 GB"). In an iPod's song list, right-click › **Copy to Library** copies the selected songs, and so does dragging them onto Music in the sidebar.
    - **Read-only:** the iPod is only ever read. Its database, `Play Counts`, `Unsub.json` and On-The-Go files are opened for reading and the music files are copied from, so nothing on it is moved, changed or deleted, and the iPod needs no write support: it works on models the sync can't write to.
    - **Where files go:** into the media folder at their organized path (Album Artist/Album/NN Title.ext), whatever "Copy files to Media folder when adding to library" says. A copy is made under a hidden name and renamed once it is whole, so a stop or a failure never leaves half a file. If the media folder's disk can't hold the songs, the copy is refused before it starts.
    - **Song info:** the iPod database's title, artist, album, album artist, genre, composer, year, track and disc numbers, compilation flag, media kind and date added are pinned over the file's tags, since users edited them in iTunes; what the iPod has nothing for stays as the file has it. Lyrics and artwork stay in the files, which carry them. An iPod with no database at all (a shuffle whose only list is its `iTunesSD`) is read from the files' own tags; art kept only in the ArtworkDB is not read.
    - **Play counts and ratings:** merged as the Music import merges them: the larger count and the later date win, a rating fills in only where the song has none, plays made in Unsub since are added on top of the iPod's, and a song's checkbox is left as it is. Doing it again changes nothing.
    - **Already in your library:** each song is matched with the same strict rules as the Music import. A sure match is left alone (its play counts are still merged). A song that fits more than one of the library's songs equally well is left out and counted as "not sure", never copied (unless "Skip songs already in my library" is off, which copies every song). A song a few seconds off one the library has may be another cut, so it is copied too and counted as "other versions". A song Unsub itself synced is known from `Unsub.json`, but only if the library still has that row and it agrees: the same title and artist with a length within three seconds, or just one of the two names with a length to the millisecond (a sync writes the library's own length to the iPod, so a song retitled since is still the same song, while the next song on the album under a reused id is not), and with no length to go on, both names. A rebuilt library, a reused id or a song deleted since is matched like any other. Songs Unsub synced get no play counts from the copy: their plays come back through the sync.
    - **Copying again:** what was copied is recorded per iPod in the library's own database (by the iPod's persistent song id, or for an iPod with no database by file path and size), in the same transaction as the songs, so a song and its record are in the library together or not at all. A record goes with its song, so a track number that is handed out again never inherits one. Copying again, or after a Stop, finds those songs there even when they can't be matched by their tags (no artist, a title like "Track 1", a length that drifts) or have been retagged since.
    - **Songs the library lost:** a song the library lists whose file has gone, on a disk that is there (a folder deleted, a drive that was reformatted), is not "already in your library": the iPod's file is copied into the media folder and the song is pointed at it, so it keeps its tags, play counts, ratings and playlists, and takes the audio details of the copy (codec, bit rate, sample rate, bit depth, channels, length) with its loudness cleared so Sound Check measures it again. A song whose file is missing because its disk isn't connected (under `/Volumes/<name>` with no such volume, or on a Windows drive that isn't there) is left alone and counted, since the disk may only be unplugged. When there are any, the sheet names the disk ("Songs on “Backup Drive”") and offers, unticked, "Restore them from the iPod anyway (if that disk is gone for good)", which restores them like any other lost song; the count follows the box. A song whose file turns up between the count and the copy is left as it is.
    - **Copy-protected songs:** FairPlay songs bought from the iTunes Store before 2009, and Audible books, play only where they were authorised, so they are skipped and counted. They are found by their `.m4p`, `.aa` or `.aax` name or the "Protected AAC audio file" or "Audible" type iTunes stored, which costs nothing, and, as each song is about to be copied, by an encrypted sample description (`drms`, `enca`, `aavd`) inside the file, so a protected song renamed `.m4a` is still caught.
    - **Playlists:** made in a folder named for the iPod ("From Riley's iPod"), including the playlists made on the iPod itself with On-The-Go. The master playlist, the podcasts list and the playlists Unsub synced are skipped. Smart playlists arrive as their current songs. Each is remembered by the iPod's own id, so copying again refills it in place, and renaming the iPod renames the folder.
    - **Running:** a background job that takes the sync's place, so a copy and a sync can't run at once, and the iPod can't be ejected while either runs. The LCD says "Reading the iPod…" from the first moment, then shows "Copying from “Riley's iPod”" with a count and Stop, which works while it is still planning. It works a few songs at a time (ten, or 64 MB, whichever is less, and never fewer than one song), so Stop leaves whole songs in the library and copying again carries on from there. An iPod pulled out part-way ends the copy with "The iPod was disconnected. 20 songs were copied." rather than a count of failures. The sheet's count reads the library under a short lock and opens no file but to size it; it only recounts when what is copied changes. It ends with a notice: "Copied 4,812 songs from Riley's iPod. 312 were already in your library. 41 are copy-protected and were left out."

14. **Other devices** — the same sync model for USB mass-storage players, Rockbox, and Android (MTP).
15. **Ship** — Windows build, installers, auto-update, Developer ID signing + notarization.
16. **Radio** — internet radio the way iTunes 10 had it: **Radio** under LIBRARY.
    - **Directory:** genre categories with disclosure triangles, then stations with their bit rate and description, from the open community directory Radio Browser (radio-browser.info: no account or key, a list of mirrors, and a User-Agent as its terms ask). Search across stations, and stations sorted by votes within a genre.
    - **Your own stations:** File › Open Stream… (⌘U) for any stream URL, plus importing `.pls` and `.m3u` files. Stations go into playlists like songs, and a Recently Played group lists the last stations heard.
    - **Streams:** Icecast/SHOUTcast over HTTP(S), with ICY metadata parsed out of the audio so the LCD shows the station and the now-playing "Artist – Title". HLS for broadcasters that only offer it. MP3, AAC, Ogg Vorbis and Opus.
    - **Playback:** a live mode in the engine. No duration or seeking; elapsed time counts up. A few seconds of buffer, reconnect on drops, and a notice when a station can't be reached.
    - **Rules:** Sound Check and crossfade don't apply to streams. Bit-perfect output still applies, for lossless streams such as FLAC-over-Icecast.
    - **Implementation note:** the bundled FFmpeg is built without its own networking. The app fetches streams itself and feeds the bytes through a custom reader, the same path a growing download uses. The directory client, ICY parsing and HLS live in a new `crates/radio`.
    - **Not planned:** recording streams.
17. **Visualizer** — View › Show Visualizer (⌘T), filling the window or the screen as iTunes' did, and moving with the music.
    - **Listening:**
      - The engine taps what's actually going to the speakers, after Sound Check, crossfade and the equalizer, and lined up with the output's latency so beats land on time.
      - Every frame it publishes a log-spaced spectrum (about 64 bands), a waveform snapshot, loudness, and beat and onset detection from spectral flux. A beat is any sudden hit that stands out of the music around it, a kick under a bass line or a snare as much as a click, found across the whole spectrum against a running threshold, so that drums in a dense mix are caught and a swell or steady noise is not.
      - The tap is read-only, so bit-perfect output stays bit-perfect.
    - **Sound around you (optional):** "React to sound" listens through the microphone instead, so it can follow a record player, an instrument or a room. It's off until chosen, and macOS asks for microphone permission when it is. Nothing is recorded or kept.
    - **Styles (our own designs, GPU-drawn with WebGL2 at the display's refresh rate):**
      - **Classic:** flowing, mirrored colour trails with feedback, in the spirit of the early iTunes visualizer.
      - **Lights:** a particle field that blooms on beats, in the spirit of iTunes 8's.
      - **Spectrum:** analyzer bars with peak caps.
      - **Scope:** an oscilloscope, including X/Y Lissajous for stereo.
      - **Album:** the cover, pulsing and tinted by the music.
      - **Pipes:** shiny pipes growing through a grid in space, turning at right angles with a ball at each corner, a few at a time in different colours; when the space is full they fade and start again. The loudness sets how fast they grow, a beat starts a pipe or makes one turn, and their hue follows the loudest band.
      - **Starfield:** flying forward through stars, faster the louder the music is, with a brief warp surge and streaks on each beat; each star is tinted and lit by one band of the spectrum.
      - **Lines:** polygons whose corners drift and bounce, leaving fading trails in slowly cycling colours; the loudness sets their speed, a beat kicks the corners, and each polygon's brightness follows the bass, the middle or the treble.
    - **Moving with the music:** every style follows the same few things: the loudness (calm when quiet, lively when loud), the bass (a pulse on each kick), and sudden sounds (flashes and sparks), so each reacts clearly without strobing.
    - **Overlay:** the now-playing title and artist fade in on each new song. Keys switch styles and toggle full screen, and Esc closes the visualizer, putting the window back if F had filled the screen. It pauses when hidden and idles when the music does.
    - **Safety:** an option to limit flashing (no more than three bright flashes a second) for photosensitive viewers, on by default.
18. **Speakers** — the speaker button at the bottom right of the window, as iTunes 10 had, to play on speakers around the house.
    - **Chromecast:** found over mDNS (`_googlecast._tcp`) and named as its owner named it. Driven with Google Cast's Default Media Receiver, which plays a link with no registration. The few CASTV2 messages this needs are written by hand over TLS, so there is no protobuf runtime in the build; a Cast device's certificate is from an authority in no trust store, so it is accepted unchecked.
    - **Sonos and other UPnP / DLNA renderers:** found over SSDP and read from their device description (Sonos by its maker, and named by its room). Driven with AVTransport and RenderingControl over SOAP, with DIDL-Lite details (title, artist, album, cover) so their displays show the song. Sonos queues the next song itself, which the others get loaded when the current one ends. A bonded room (a stereo pair's other half, a home theater's sub and surrounds) or a room grouped with another is not listed on its own: only the speaker that takes the commands is, read from Sonos's zone topology and named as the Sonos app names a group ("Kitchen + Bedroom"). Descriptions are fetched from the machine that answered the search, without following redirects, and a service whose control address is on another machine is ignored.
    - **AirPlay (macOS):** there is no AirPlay 2 sender library, and the pairing is not ours to reverse-engineer. AirPlay speakers, HomePods included, are outputs of the Mac itself, so "AirPlay…" opens the Sound pane of System Settings, where one is chosen, and the engine follows the system's output wherever it moves. The menu checks "AirPlay…" while the Mac's output is one, unless bit-perfect output is on: that holds the device it started on, so the entry says to turn it off first. Windows has no AirPlay for now, and the menu says so.
    - **The menu:** a native popup with Computer, then the speakers grouped as Chromecast, Sonos and Other speakers, the one playing checked. While one plays, the LCD's second line takes "Playing on Kitchen" into its rotation and the button turns blue.
    - **Switching:** choosing a speaker connects to it first, so one that can't be reached leaves the music where it was. Then the engine stops and the song carries on from the same place on the speaker, paused if it was. Choosing another speaker or Computer again does the same the other way. The play queue, play counts and bookmarks carry on as they were; the speaker's driver reports the same events the engine does.
    - **Playing:** the app drives the queue. It loads each song, reads the speaker's status about twice a second, and moves on when a song ends. Converting a song happens on a helper thread, so the speaker keeps being listened to and answered meanwhile, and a conversion nobody wants any more is cancelled. If the speaker starts playing something that isn't from our own link server (another app on the Sonos), casting ends there and that song is left alone; the first few seconds after each change are given the benefit of the doubt, since some renderers go on naming the previous song for a poll or two. Pause, resume and seek while a song is still being made ready are about that song, and a song that ends meanwhile is followed by it. Play, pause, seek and the volume slider act on the speaker, whose own volume the slider shows. Gapless playback and crossfade are not offered; Sonos is told the next song early, so it usually is gapless anyway.
    - **Formats:** what a speaker can play is sent as it is: MP3, AAC, FLAC and Ogg Vorbis, and Opus to a Chromecast, up to 48 kHz and (FLAC) 24 bits. Anything else (ALAC, AIFF, Opus to Sonos, WavPack, high resolution) is converted to FLAC at 48 kHz or below and 24 bits or below by the existing converter, into a temporary file that is deleted when the speaker is done with it.
    - **Serving:** the speaker fetches songs over HTTP from the Subsonic server's own machinery, started as a second, separate server only while a speaker is chosen, whether or not library sharing is on. It listens on the one interface that reaches the speaker, serves only the song playing and the one queued (and their covers), each at a link with a 128-bit random secret that is closed the moment it is not needed and lapses after ten idle minutes, and serves nothing else of the library.
    - **Off while casting:** the visualizer and the equalizer can't hear what the speaker plays. The visualizer shows the Album style with a note, the equalizer says it has no effect, and Sound Check and crossfade don't apply. Stations still play on the computer.
    - **Failures:** a speaker that goes missing, drops off the network or is taken over by another app stops the music cleanly (a speaker that never completes the connection is given up on after a few seconds); the app goes back to Computer and says so in the LCD. Quitting stops the speaker rather than leaving it playing to a server that is gone.
